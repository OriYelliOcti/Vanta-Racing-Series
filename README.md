# Vanta Racing Series — league site

A static site for the VRS Roblox racing league. No framework, no build step, no
server: plain HTML, CSS and JavaScript plus JSON files in `data/`. It runs on
GitHub Pages exactly as it is.

| Page | What it does |
|---|---|
| `index.html` | Season overview, F1 championship top five, next round, latest steward decisions |
| `grid.html` | Every team and every seat, filterable by division, team, slot and open/filled |
| `races.html` | Timing sheets, driver and constructor standings, position/points/wins/podiums |
| `fantasy.html` | Build a fantasy team of two drivers plus one constructor, lock in, get a code |
| `schedule.html` | Calendar with circuit, country, lap count and pit window |
| `stewards.html` | Protected desk: publish decisions and clips through a local bridge |

## Local preview

```bash
cd vrs-site
python -m http.server 8080
# open http://localhost:8080
```

Opening the HTML files directly with `file://` will not work — `fetch` cannot read
the JSON data from the filesystem.

## Publish on GitHub

```bash
git init
git add .
git commit -m "Vanta Racing Series site"
git branch -M main
git remote add origin git@github.com:<you>/<repo>.git
git push -u origin main
```

Then GitHub → Settings → Pages → *Deploy from a branch* → `main` / `/ (root)`.
`.nojekyll` is already there so the `assets/` folder is served untouched.

## Data files

Everything the site shows comes from `data/`.

- **`config.json`** — league name, season, divisions, slot definitions (code,
  label, capacity), scoring table, bridge default URL, sync interval.
- **`lineups.json`** — generated by `tools/sync_lineups.py` from Discord roles.
  Never edit by hand if the sync is running.
- **`schedule.json`** — one entry per round: `round`, `name`, `circuit`,
  `country`, `laps`, `pitWindow`, `date`.
- **`results.json`** — one entry per round with `divisions.F1` / `divisions.F2`
  arrays of `{pos, driver, team, fastestLap?, pole?, note?}`. Points are
  calculated in the browser from these rows.
- **`decisions.json`** — steward decisions and the audit log. Written by the
  bridge, never by the website.
- **`fantasy.json`** — published fantasy entries (`code`, `owner`, `drivers`,
  `constructor`, `lockedAt`). Written by the bridge after the codes are
  collected in Discord.

Placeholder content is flagged: rounds in `results.json` with `"demo": true` show a
**Demo data** banner, and `schedule.json` carries a `_note` saying the calendar is
a placeholder. Replace both before the season starts.

## Lineups every five hours

`tools/sync_lineups.py` reads the guild roles, matches each member's team role and
staff role, and rewrites `data/lineups.json`. It only fills a seat when someone
carries **both** the team role and the slot role — no guessing.

```bash
# once, to check
python tools/sync_lineups.py

# cron: every five hours, then publish through the bridge
0 */5 * * * cd ~/vrs-site && ~/vanta-bot/.venv/bin/python tools/sync_lineups.py --push
```

Environment: `VRS_GUILD_ID`, `VRS_TOKEN_FILE` (file containing the bot token),
`VRS_BRIDGE`, `VRS_BRIDGE_TOKEN`.

## Fantasy flow

1. Player picks two drivers and one constructor on `fantasy.html`.
2. Lock-in produces a code such as `VRS-7K3QM`, derived from the picks — the same
   picks always produce the same code.
3. The player submits it in Discord: `/fantasy code: VRS-7K3QM`.
4. The bridge writes the entry into `data/fantasy.json` (owner, picks, code).
5. The site scores every published entry against the same results the race centre
   uses, so fantasy points and championship points never drift apart.

The bot command itself is not part of this repository; it only has to hand the
code to the bridge.

## Stewarding desk and the bridge

The desktop never gets write access to the repository. `stewards.html` asks for a
**bridge URL** and a **personal bridge token**, then talks only to that bridge —
a small application running on the steward's own laptop that holds the git
credentials and commits the change.

Protocol (implement it in the bridge):

```
GET  {bridge}/whoami
     Authorization: Bearer <token>
  -> { "owner": "Octi" }

POST {bridge}/publish
     Authorization: Bearer <token>
     { "kind": "decision", "entry": { round, type, subject, text, clip } }
  -> { "ok": true, "commit": "<sha>", "owner": "Octi",
       "decision": { ...entry, by, publishedAt },
       "audit": { at, actor, action, target } }

POST {bridge}/publish
     { "kind": "lineups" | "fantasy", ... }
```

Rules the bridge must enforce:

- The token decides the actor name. The browser never sends a name and cannot
  spoof one — the audit log records the identity that owns the token.
- Tokens live on the laptop, not in this repository. Nothing in the site stores a
  token: it is kept in `sessionStorage` for the current tab only.
- Reject unknown `kind` values and empty rulings.
- Commit with a message naming the token owner, then return the commit SHA.
- Allow the Pages origin in CORS (`Access-Control-Allow-Origin`), otherwise the
  desk cannot reach the bridge.

If the bridge is not running, the desk shows the error and the repository stays
untouched; "Download decisions.json" is the manual fallback.
