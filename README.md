# Vanta Racing Series — league site

A static site for the VRS Roblox racing league. No framework, no build step, no
server: plain HTML, CSS and JavaScript plus JSON files in `data/`. It runs on
GitHub Pages exactly as it is.

| Page | What it does |
|---|---|
| `index.html` | Season overview, F1 championship top five, calendar preview, latest steward decisions |
| `grid.html` | Every team and every seat, filterable by division, team, slot and open/filled |
| `races.html` | Timing sheets, driver and constructor standings, position/points/wins/podiums |
| `fantasy.html` | Build a fantasy team of two drivers plus one constructor, lock in, get a code |
| `schedule.html` | The season calendar: country flag, country and circuit per round |
| `stewards.html` | The FIA desk — hidden extra, password only, publishes through a local bridge |

## Data files

Everything the site shows comes from `data/`.

- **`config.json`** — league name, season, divisions, slot definitions (code,
  label, capacity, which teams own them), scoring table, bridge URL, sync interval.
- **`lineups.json`** — generated by `tools/sync_lineups.py` from Discord roles.
  Never edit by hand if the sync is running.
- **`schedule.json`** — one entry per round: `round`, `flag`, `country`,
  `circuit`. The calendar carries no dates or times: those are announced in
  Discord, and `_note` says further rounds may be added.
- **`results.json`** — one entry per round with `divisions.F1` / `divisions.F2`
  arrays of `{pos, driver, team, fastestLap?, pole?, note?}`. Points are
  calculated in the browser from these rows. Empty until the first race weekend.
- **`decisions.json`** — steward decisions and the audit log. Written by the
  bridge, never by the website.
- **`fantasy.json`** — published fantasy entries (`code`, `owner`, `drivers`,
  `constructor`, `lockedAt`).

Rounds in `results.json` flagged `"demo": true` would show a **Demo data** banner;
none are published. Fantasy picks come from the lineup drivers, so the
championship is playable before the first points are scored.

## Lineups every five hours

`tools/sync_lineups.py` reads the guild roles, matches each member's team role and
staff role, and rewrites `data/lineups.json`. It only fills a seat when someone
carries **both** the team role and the slot role — no guessing.

```bash
# once, to check
VRS_TOKEN_FILE=~/vrs-token.txt python tools/sync_lineups.py

# cron: every five hours
0 */5 * * * cd ~/vrs-site && ~/vanta-bot/.venv/bin/python tools/sync_lineups.py
```

Environment: `VRS_GUILD_ID`, `VRS_TOKEN_FILE` (file containing the bot token),
`VRS_BRIDGE`, `VRS_BRIDGE_TOKEN`.

## The FIA desk (the extra door)

The desk is not in the navigation. It opens from:

<https://oriyelliocti.github.io/Vanta-Racing-Series/#vrs-FIA>

Access: the FIA password the league uses. The page asks for that one secret and
nothing else — no bridge token, no GitHub login.

Publishing goes through the hosted bridge in `desk-worker/`, deployed on Freebuff
Sites at `https://vrs-fia-desk-bridge-8jkzgx-preview.freebuff.site` and set as
`bridge.defaultUrl` in `data/config.json`. That deployment needs the `GITHUB_TOKEN`
secret (a token with **Contents: read and write**) and `DESK_PASSWORD`; the page
never sees either.

The bridge checks the password and publishes two things:

- **Steward decisions** — appended to `data/decisions.json` plus the audit log.
- **Race results** — the desk has a result editor: pick the round and division, put
the drivers in finishing order (fill from the lineup in one click, mark fastest
lap and pole), press Publish. `data/results.json` is updated and the championship,
home page and fantasy recompute from it. Publishing again for the same round and
division replaces that result, so corrections are just another publish.

The bridge commits to `main` through the GitHub API and Pages publishes it about a
minute later. A rejected write commits nothing, so the repository is never left
half-published.

Options: `--port`, `--password` (or `VRS_DESK_PASSWORD`), `--token-file` (default
`../github token.txt`, `VRS_DESK_TOKEN_FILE`), `--dry-run` (validate and answer
without writing or pushing), `DESK_NAME` (name in the audit log, defaults to
`git config user.name`).

### Local bridge (only for the host laptop)

`tools/desk_server.py` is the same API on loopback, useful when the laptop is the
one doing the publishing:

```bash
cd vrs-site
python tools/desk_server.py
# http://127.0.0.1:8787/stewards.html#vrs-FIA
```

It pushes with the laptop's Git credential, so it needs no token. A Startup script
keeps it running after a reboot:

```
%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\vrs-desk-bridge.cmd
```

It runs `pythonw tools/desk_server.py --log-file logs/desk-bridge.log` without a
console window. Important: `127.0.0.1` is the machine that opens the page, so only
that laptop can use the local bridge — every other steward uses the hosted one.

Endpoints:

```
GET  /health              -> {"ok": true, "owner": "…", "dryRun": false,
                             "acceptsToken": true}
POST /unlock   {password} -> {"ok": true, "owner": "…"} | 401
POST /publish  {password, kind: "decision", entry: {round, type, subject, text, clip}}
POST /publish  {password, kind: "result", entry: {round, division,
               rows: [{pos, driver, team, fastestLap?, pole?, note?}]}}
                          -> {"ok": true, "commit": "<sha>", "owner": "…",
                              "decision"|"result": {…}, "audit": {…}}
```

`password` is the field name for the secret, whether the caller sends the FIA
password or the token.

CORS is allowed for the Pages origin and for `localhost`/`127.0.0.1`, so the same
desk works from the published site and from the bridge itself. Without the bridge
the site keeps working; only publishing stops, and "Download decisions.json" is the
manual fallback.

## Fantasy flow

1. Player picks two drivers and one constructor on `fantasy.html`.
2. Lock-in produces a code such as `VRS-7K3QM`, derived from the picks — the same
   picks always produce the same code.
3. The player submits it in Discord: `/fantasy code: VRS-7K3QM`.
4. The steward imports the entries into `data/fantasy.json` as `{code, owner,
   drivers, constructor, lockedAt}`.
5. The site scores every published entry against the same results the race centre
   uses, so fantasy points and championship points never drift apart.
